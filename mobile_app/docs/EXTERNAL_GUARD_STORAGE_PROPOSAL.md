# Guest-booking guard storage: final design (Upstash Redis REST)

Status: implemented in `mobile_app/edge-function-draft/guest-create-service-request.js` and covered by sandbox (mocked) tests only. Nothing has been provisioned, deployed or written live. Controlled integration testing only; not production.

## Decisions
- **Storage:** Upstash Redis through its HTTPS REST API (`POST <UPSTASH_REDIS_REST_URL>`, `Authorization: Bearer <UPSTASH_REDIS_REST_TOKEN>`, JSON command array body; response `{result}` or `{error}`). TLS only: a non-`https://` URL counts as missing config. No Apper guard table (`GUARD_TABLE_PROPOSAL.md` is superseded).
- **Secrets:** five server-side secrets on Apper's Secrets page, read only through `await apper.getSecret(NAME)` in `loadConfig()`: `APPER_API_KEY`, `APPER_APP_ID`, `GUARD_HMAC_SECRET`, `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`. Any missing/empty value, or `getSecret` throwing, returns 503 `Booking is temporarily unavailable` with nothing created. The return shape of `getSecret` is **assumed** to be a string (a `{ value }` wrapper is accepted defensively); verify it in Apper before deploy.
- **Identifiers:** HMAC-SHA256 with `GUARD_HMAC_SECRET`, domain prefixes `phone:`, `idem:`, `payload:`, hex truncated to 32 characters. Keys are `idem:<h>` and `rate:<phoneH>:<yyyymmddhh>`, where the hour bucket is **UTC**. The payload hash covers canonical sorted-key JSON of `{serviceKey, mobile (normalised +91), fullName, location, coordinates, serviceDetails (server-validated)}`. Redis never holds a raw phone number, attempt key, name or address. Keep `GUARD_HMAC_SECRET` stable: rotating it orphans existing keys.
- **Claim + rate limit (one atomic script):** 5 new booking claims per phone per UTC hour. A single Lua `EVAL` (`CLAIM_AND_RATE_SCRIPT`, KEYS = idem key, rate key; ARGV = pending-claim JSON, 604800, 7200, 5) does: if the idem key exists, return `{0, existingValue}`; else if the current rate count is already >= 5, return `{2, count}` **without incrementing and without creating a claim** (HTTP 429); else `INCR` the rate key (`EXPIRE 7200` on the first hit) and `SET` the idem key `NX EX 604800`, returning `{1, newCount}`. So concurrent submissions with the same attempt key consume at most one attempt, a retry of an existing claim never consumes an attempt, over-limit attempts do not increment the counter, and a claim only exists together with its rate increment. No `cjson`.
- **No duplicate-by-phone block:** two different consecutive bookings from one phone are allowed; only the attempt key deduplicates.
- **Retention:** pending claims `PENDING_TTL_SECONDS = 604800` (7 days); completed claims `COMPLETED_TTL_SECONDS = 604800` (7 days, which meets the 24-hour minimum).

## Flow (createBooking)
1. Validate input (400 on failure) and load config (503).
2. Run the claim-and-rate script once (this is the only decision path; there is no separate `GET`, rate `EVAL` or `SET NX`). `{0, value}`: answer the existing claim (below) without creating anything. `{2, count}`: 429. `{1, count}`: this invocation owns the new pending claim `{state:'pending',payloadHash,stage:'claimed',createdAt}`. Any Redis error or malformed script result: 503 before any Apper call.
3. Look up the category/capability and the customer by `phone_c` (reads only; a failure here happens before any write and releases the claim). A phone match whose `Id` is unusable is also treated as a lookup failure (released, no profile created).
4. If no profile exists, create it (customer fields are exactly `Name, phone_c, location_c, status_c`; no email, Owner or coordinates). An explicit rejection (HTTP 4xx or per-record `success:false`) releases the claim (503). An **uncertain** customer create (network error/timeout, 5xx, unparseable body, success without a valid UUID `Id`) does **not** release: the claim is compare-and-set to `stage:'customer-write-uncertain'` (TTL preserved), the request create is not attempted, and the reply is the HTTP 202 pending answer. Otherwise, a compare-and-set to `stage:'request-writing'` with `customerId` (TTL preserved), then the single service-request create.
5. Success: compare-and-set to `{state:'done', requestId, payloadHash}` with `EX 604800`, and return `{success:true, requestId, message}`.
6. **Definitive failure** (a lookup read failed before any write, the customer create or the request create got an explicit 4xx or per-record `success:false`, or the `request-writing` stage update failed before the request write): compare-and-delete the claim and return a generic 503 so the user can retry with the same key.
7. **Uncertain failure** (network error or timeout, 5xx, unparseable response, or a missing/invalid Id after the customer create or the request create; or failing to record `done` after the request was created): the claim stays **pending** (`stage:'customer-write-uncertain'`, or `stage:'request-write-uncertain'` with the `requestId` if known). Nothing is deleted and the Apper write is never retried. The response is HTTP 202 `{success:true, pending:true, status:'pending', message:'Your booking is being confirmed. Please do not submit it again. Customer Care will confirm it.'}`.

Existing-claim answers: same payload and `done` returns the original `requestId` with `duplicate:true`. A different payload returns 409 `This booking attempt key was already used for a different request`. `pending` returns the 202 above and never creates anything.

**Pending needs manual reconciliation.** A pending claim blocks that attempt key for its full 7-day retention. There is no automatic resubmission. Customer Care must check in the Admin Panel whether the request exists and confirm it with the customer. Deleting a pending key by hand, if ever needed, needs a separate decision.

Compare-and-set/delete scripts replace or delete the key only if it still holds **exactly** the pending value this invocation wrote. That value contains `state:'pending'` and the `payloadHash`, so this is at least as strict as "pending and same payloadHash", and it does not depend on Lua `cjson`.

## Honest guarantees
Each Redis command or script is atomic on its own. The full booking (Redis claim, Apper customer write, Apper request write) is **not a distributed transaction** and has **no exactly-once guarantee**. A crash or timeout between steps can leave a pending claim, an orphan customer profile, or a created request whose claim never reached `done`. A duplicate customer profile is possible only if a customer write that was left pending (`customer-write-uncertain`) actually succeeded; Customer Care must reconcile such a pending claim manually (check the Admin Panel for the profile) before any new attempt for that customer. Caveat (unchanged behaviour, unverified live): when a customer profile was created with a confirmed Id but the claim is then released (explicit request rejection, or the `request-writing` stage update failing), the retry depends on Apper's phone lookup already returning that new profile; if Apper's read-after-write were delayed, a second profile could still be created. The design fails toward "pending, reconcile by hand" rather than toward creating a duplicate. The per-phone limit does not stop an attacker who rotates phone numbers (accepted residual risk for controlled testing, since the function is invoked without authentication).
