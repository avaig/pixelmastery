# Known limitations

- Only Car Wash has an in-app customer booking flow. Car Service, Car Essentials and Insurance Claim screens clearly say **Coming soon on mobile** and do not fabricate menu data or create bookings.
- Admin and Service Provider authentication is not implemented. The account screen is a status placeholder. No username/password form is present.
- Customer Care phone number is not supplied. `EXPO_PUBLIC_CUSTOMER_CARE_PHONE` is optional; the app will not dial an invented number when it is blank.
- The edge function can only be exercised against live Apper after deployment and configuration of server-side `APPER_API_KEY` and `APPER_APP_ID`. No live credentials are available in the build sandbox.
- `device_type_c` is set to the existing web app value `Mobile`. The API field’s live picklist was not read from the deployed schema; `Mobile App` is not used without verification.
- `customer_profiles_c` has no coordinate fields (verified live), so only request records receive coordinates. Exact verified live picklist write values: customer/provider status `Active`, request status `Open`, preferred time `ASAP`, service mode `Normal`, pricing mode `Fixed Price`, provider verification `Approved`, availability `Available Now` / `Available Later`, capability-link status `Active` / `Approved`. The `Car Assistance` category and `Car Wash` capability lookup names/rows are **not verified** against live records; confirm before deploy. `device_type_c` value `Mobile`, other field types, lookup behavior, and end-to-end writes remain unverified.
- Guest bookings require the **unprovisioned** internal `guest_booking_guard_c` table and server-only `GUARD_HMAC_SECRET`. Until both are configured, bookings fail closed (503). The guard uses domain-separated HMAC-SHA256 keys, a `Pending` claim and read-back lowest-Id election, followed by `Done` or `Failed` updates. It remains **best-effort, NOT PRODUCTION-GRADE**: no atomic unique insert or transaction is documented; read-after-write consistency and concurrent duplicate protection are unverified. See [GUARD_TABLE_PROPOSAL.md](GUARD_TABLE_PROPOSAL.md) for schema, permissions, retention, secret rotation and pre-live checks. No guard markers are put in the customer-facing problem description.
- The guest customer and service request writes are separate operations. If the customer profile is created but the request write fails, retries look up by phone before creating a profile, but the flow is not transactional. A newly created guest customer profile may remain without a linked request.
- Nearby provider reads are capped at 500 technician profiles and 1,000 capability links per invocation. Results are filtered by approved verification, Active status, availability, Car Wash capability, provider radius and discovery radius. Data beyond those paging caps is not considered.
- Nearby map shows the user’s search circle only. Provider exact coordinates, phone numbers and record IDs are intentionally not returned by the API; the list uses a first name and rounded distance.
- Manual addresses may be geocoded on-device (Android needs foreground permission for geocoding; declining is allowed; platform availability/results are not guaranteed) or located with a draggable map pin. Those coordinates are not independent proof of address accuracy; any coordinates outside 25 km are rejected by both app and server. If no coordinates are available, the request location is prefixed `[LOCATION VERIFICATION PENDING] ` and the app warns that Customer Care must verify it before dispatch or provider offers. **Risk to confirm:** existing web matching may treat no-coordinate requests as eligible to all providers because it applies radius only when both parties have GPS. Do not run any offer flow until Customer Care verifies location. The location prefix is truncated to fit a 220-character location field; actual field length is not independently verified.
- App icon and splash artwork are Pillow-generated placeholders. `com.local.mobile` / `com.local.mobile` are placeholder package identifiers.
- Native GPS, iOS/Android map rendering, restricted Google Maps keys, EAS production signing, Accessibility review and authentication remain untested.
